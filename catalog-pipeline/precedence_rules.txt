- Default rule: most-specific kind wins. Match the repo's PRIMARY artifact (what the repo exists to be), not secondary features it happens to have.
- AI agent vs AI model: if it orchestrates an LLM to act (agent harness, agent platform, agent framework/SDK, skill pack) -> ai-agent-tooling. If it trains/serves/ships/applies a model (weights, inference server, ML/CV framework, generative app) -> ai-ml-runtime. The 'is it an agent or a model?' question is decided first.
- Anything AI/ML beats generic buckets: an ML training framework -> ai-ml-runtime, NOT dev-tools or backend-infra. An agent tool -> ai-agent-tooling, NOT dev-tools. AI-specific kinds outrank dev-tools/backend-infra/self-hosted-app.
- Platform-to-build-on vs app-to-use: if other software is built on top of it (backend, datastore, orchestration, server framework) -> backend-infra. If the end user runs it directly as the product -> self-hosted-app. When both seem true, pick by primary use: 'do I build with this, or do I use this?'
- Framework/library vs finished product: a reusable framework/library/kit -> its framework kind (frontend-ui, cross-platform-app, backend-infra, ai-ml-runtime). A finished application -> self-hosted-app. The thing you import != the thing you deploy.
- Native vs web rendering: produces native desktop/mobile/game binaries -> cross-platform-app. Renders web/browser UI -> frontend-ui.
- Narrow CLI vs broad toolchain: one sharp single-purpose command-line tool -> cli-utility. A rich developer tool, IDE, SDK, terminal, or productivity suite -> dev-tools. Package/version managers count as cli-utility even though developers use them.
- Networking job beats generic: if the core job is moving traffic/sessions/streams (proxy, tunnel, remote control, mirroring, transfer, stream aggregation) -> networking-media, even though it could be called a tool or self-hosted app. A media DOWNLOADER (grabs files) -> cli-utility; a media STREAM/session tool -> networking-media.
- Teaching arc vs static curation: structured lessons/courses/roadmaps/build-it tutorials/annotated reference impls meant to teach a human -> learning-resource. Static lists/indexes/specs/datasets/style-guides meant to be referenced -> curated-knowledge. If there's no learning progression, it's curated-knowledge.
- Language/runtime is the floor: a language, compiler, VM, emulator, or OS kernel -> language-runtime, even though everything is 'built in a language'. A web framework or backend written IN a language -> backend-infra.
- Content vs code: if the repo has a real runnable artifact, file it by what the software DOES, not its theme. social-manifesto and curated-knowledge are only for repos with little/no functional code.
- Docs do not move a repo: a working tool/library/app with excellent documentation or tutorials stays in its functional kind; it does NOT become a learning-resource.- Object storage (S3-compatible blob/file stores like minio, seaweedfs) is NOT a database-engine — file under backend-infra as storage/object-store, not database-engine (databases store queryable structured data).
- A static site / docs generator (hexo, hugo, jekyll, docusaurus) is NOT a web-build-bundler — file as docs-site-generator. Bundlers (webpack/vite/rollup) bundle JS modules; SSGs render content to a site.
- A mature domain framework/platform (trading platform, CMS, ERP with engines/gateways) is NOT a fullstack-app-starter/boilerplate. Boilerplate = a thin scaffold you clone to START a project; a framework with real subsystems is its own kind.
